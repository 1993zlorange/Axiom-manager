# Axiom-manager 项目更新规则

适用于读取本项目 AGENTS.md 的编码助手。安装表示授权助手在完成本次用户任务后，按以下规则创建本地 Git 提交；远端推送依项目配置执行。用户当次明确要求只分析、暂不提交或暂不发布时，遵守当次要求。

## 完成一次任务后

1. 开始工作时查看 Git 状态，识别并保留用户已有修改。只提交本次任务完成且验证过的内容；同一文件混有旧改动且无法可靠分离时，说明情况，保留原内容和暂存区。
2. 完成一项可独立说明的功能、修复或文档修改后，运行相关验证。真实记录通过、失败和未运行的检查；检查失败时先修复，不把未完成内容描述为完成。
3. 检查 README、配置示例及 CHANGELOG 是否仍准确；用户可见的新增、修复或不兼容变化写入 CHANGELOG 的 `## [Unreleased]` 段。相关代码、测试和文档作为同一项修改提交。
4. 在项目根目录运行 `python .axiom-manager/manage.py status`，再用 `python .axiom-manager/manage.py commit --message "类型(范围): 中文说明" --files 本次文件路径 --write` 完成检查和提交。逐项列出文件，重命名包含新旧路径。没有改动时跳过。
5. 最后简要报告修改、实际验证和提交短哈希；若执行了推送或发布，分别报告结果。提交或推送失败时保留工作区，说明已完成到哪一步及处理办法，不宣称成功。

## 中文 Commit

格式为 `type(scope): 中文说明`，范围可省略。使用英文半角括号、冒号和空格；类型使用小写英文，说明以中文为主，技术名称可保留英文。

- 功能与修复：`feat` 新功能、`fix` 问题修复、`perf` 性能改进。
- 文档与内部调整：`docs` 文档、`refactor` 不改变外部行为的重构、`test` 测试、`style` 代码格式。
- 工具与维护：`build` 构建或依赖、`ci` 自动化流程、`chore` 其他维护、`revert` 撤销。

一句话写出具体动作、对象和结果，中文描述建议不超过 30 字，完整标题不超过 72 个 Unicode 字符。避免“更新代码”“修复问题”等空泛标题。简单修改只写标题；复杂修改在空行后的正文说明原因、影响和实际验证结果。多行信息用 UTF-8 文件配合 `--message-file`，避免命令行转义问题。

例如：`feat(git): 支持任务完成后自动提交`、`fix(install): 修复重复安装导致规则重复的问题`、`docs(readme): 补充 Windows 卸载命令`。

不兼容修改在标题冒号前加 `!`，并在空行后使用大写 `BREAKING CHANGE: 中文影响与迁移办法`。例如 `feat(config)!: 将 push 字段改为 auto_push`，正文说明旧配置如何迁移。

## 版本和发布

采用语义化版本 `主版本.次版本.修订版本`，标签为 `v1.2.3`，版本文件为 `1.2.3`。主版本表示不兼容变化，次版本表示兼容新功能，修订版本表示兼容修复。一次发布按累计变化中的最高级别升级一次，低位归零。

每次任务完成都提交；仅用户要求发布、打包交付或项目已有发布授权时执行 `release`，日常提交不自动发版。文档、测试和内部整理默认不发版。0.x 阶段不兼容变化升级次版本；首个开发版本建议 0.1.0，稳定后通过显式版本发布 1.0.0。

优先使用现有权威版本来源。未配置时检查根目录 package.json、pyproject.toml 和 VERSION；有多个来源时必须一致，否则先处理冲突。动态版本、多个独立产品或复杂工作区需要在 `.axiom-manager/config.json` 显式配置，不能猜测或覆盖其他产品的版本。

发布前确保工作区干净、README 准确、待发布更新说明完整。先运行 `python .axiom-manager/manage.py release` 预览，再在已获发布授权的范围内加 `--write` 执行；脚本同步受支持版本文件和 npm 项目锁文件、整理 CHANGELOG、提交并创建附注标签。预发布或跨到 1.0.0 用 `--version 0.2.0-beta.1` 或 `--version 1.0.0` 明确指定。已有标签保持原样。

## README 和更新日志

README 面向项目使用者，保留现有合理结构，按实际情况介绍：用途和状态、安装与升级、快速使用与配置、验证和常见问题、卸载及相关文档入口。命令、默认值、路径、环境要求和兼容性必须对应真实实现，仓库内链接优先使用相对路径。

安装、启动、用法、配置、默认值或兼容性变化时，同步对应说明和示例。内部重构或测试调整也要检查 README；内容仍准确时不为凑更新而修改。不把未实现功能写成已支持，不在 README 堆积完整提交历史或内部过程记录。

CHANGELOG 使用 UTF-8 Markdown，以 `## [Unreleased]` 保存待发布的用户变化，按新增、修复、改进、不兼容变化组织。发布后归入 `## [版本号] - YYYY-MM-DD`，日期按 Asia/Shanghai。复杂的不兼容变化保留迁移步骤；历史已发布记录不改写。

## 配置、失败和能力边界

`.axiom-manager/config.json` 的 `checks` 为逐条运行的命令参数数组，用 `{python}` 代表当前 Python。先配置项目适用的测试或验证命令。确实没有适用命令时，使用 `--no-checks-reason "原因及实际检查方法"`，不得借此绕过失败的已配置检查。

默认 `auto_push=false`，只提交本地。项目明确启用 `auto_push` 后按指定 `remote`、`branch` 推送，无需每次重复询问。推送失败时本地提交仍有效，使用 `push --write` 重试；发布标签使用 `push --tag v版本 --write`，不重复创建提交。

已有暂存内容、未解决冲突、未完成 Git 操作或缺少身份配置时，先保留现场并说明原因。尚未初始化 Git 的项目，先说明情况；在用户已授权创建项目仓库时可执行初始化。备份不纳入提交。默认不改写历史，恢复操作应保留用户未提交内容。

AGENTS.md 指导读取它的助手执行流程，不是后台文件监控器。脚本检查格式、文件和版本一致性，助手仍须判断说明是否准确、文档是否需要更新以及哪些改动属于本次任务。
